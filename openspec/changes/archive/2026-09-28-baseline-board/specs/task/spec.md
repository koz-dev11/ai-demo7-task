## Purpose

認証なしの公開タスクボードとして、メンバーの登録・一覧・削除と、タスクの登録・一覧・詳細・削除を提供する。登録されたタスクの担当者はサーバが割り当てる。個人情報・社外秘は入れない。

## ADDED Requirements

### Requirement: 一段目は認証を要求しない
システムはログインを要求してはならない。`/login` を提供してはならない。誰でもメンバーとタスクを読み書き・削除できることが必須である。ユーザー識別情報は持ってはならない。

#### Scenario: 未ログインで操作できる
- **とき** 未ログインの利用者がメンバーの登録と、タスクの登録・一覧・詳細・削除を行う
- **ならば** 認証画面やログイン要求は出ない
- **かつ** 操作は完了する

### Requirement: 画面ルートは 4 つだけである
システムが提供する画面ルートは `/`、`/new`、`/tasks/:id`、`/members` だけであることが必須である。`/login` と `/members/:id` を足してはならない。未知のパスは、見つからないことが分かる表示で必須である。

#### Scenario: 未知のパスは見つからない
- **とき** 利用者が `/login` または `/members/anything` またはその他の未知パスを開く
- **ならば** 見つからないことが分かる
- **かつ** メンバー一覧やタスク一覧としては扱わない

### Requirement: タスク一覧は / である
システムは画面 `/` でタスク一覧を必須で出す。並びは `createdAt` の降順で必須である。各項目は担当者名、完了、作成日時を必須で示す。カードからそのタスクの詳細 `/tasks/:id` へ必須で遷移する。タスクが無いときは、タスクが無いことが分かる表示で必須である。タスク登録への導線は必須である。一覧に削除を置いてはならない。メンバー絞り込みを置いてはならない。完了の切り替えを置いてはならない。担当者の変更を置いてはならない。

#### Scenario: 空のタスク一覧
- **とき** タスクがまだ無い状態で `/` を開く
- **ならば** タスクが無いことが分かる
- **かつ** タスク登録への導線がある
- **かつ** 削除操作は無い

#### Scenario: 一覧は新しいタスクが上である
- **とき** 作成日時が異なるタスクが 2 件以上ある状態で `/` を開く
- **ならば** `createdAt` が新しいタスクが上に出る
- **かつ** 各項目に担当者名、完了、作成日時が出る
- **かつ** カードからそのタスクの詳細へ遷移できる
- **かつ** 一覧に削除は無い

### Requirement: タスク登録は /new である
システムは画面 `/new` でタスク登録を必須で提供する。タイトルは必須である。担当者を選ばせてはならない。登録に成功したならば一覧 `/` へ必須で戻る。完了の入力を出してはならない。

#### Scenario: タイトルは必須である
- **とき** 利用者がタイトル空のまま `/new` で登録しようとする
- **ならば** タスクは追加されない
- **かつ** タイトルが必須であることが分かる

#### Scenario: 担当者は選ばせない
- **とき** 利用者が `/new` を開く
- **ならば** 担当者を選ぶ入力は無い
- **かつ** タイトルを入れて登録に成功すると `/` へ戻る

### Requirement: タスク詳細は /tasks/:id である
システムは画面 `/tasks/:id` で、そのタスクのタイトル、担当者名、完了、作成日時を必須で出す。削除は confirm のあとだけ実行することが必須である。削除に成功したならば `/` へ必須で戻る。存在しない id は、見つからないことが分かる表示で必須である。担当者の変更を出してはならない。完了の切り替えを出してはならない。

#### Scenario: 詳細を見て confirm 後に削除する
- **とき** 利用者が存在するタスクの詳細を開き、削除を confirm する
- **ならば** そのタスクはハード削除される
- **かつ** `/` へ戻る
- **かつ** 一覧にそのタスクは無い

#### Scenario: confirm を拒否すると削除されない
- **とき** 利用者が詳細で削除を始め、confirm を拒否する
- **ならば** タスクは残る
- **かつ** 画面は詳細のままである

#### Scenario: 存在しないタスクは見つからない
- **とき** 利用者が存在しない id の `/tasks/:id` を開く
- **ならば** 見つからないことが分かる

#### Scenario: 詳細に担当者変更と完了切替は無い
- **とき** 利用者がタスク詳細を見る
- **ならば** 担当者を変える操作は無い
- **かつ** 完了を切り替える操作は無い

### Requirement: メンバー画面は /members だけである
システムは画面 `/members` で、メンバーの登録と一覧と削除を必須で提供する。一覧は `createdAt` の降順で必須である。削除は confirm のあとだけ実行することが必須である。メンバーの詳細画面を提供してはならない。メンバーが無いときは、メンバーが無いことが分かる表示で必須である。

#### Scenario: メンバーを登録して一覧に出る
- **とき** 利用者が `/members` で名前を登録する
- **ならば** そのメンバーが一覧に出る
- **かつ** 新しいメンバーが上に出る
- **かつ** 詳細画面へは遷移しない

#### Scenario: メンバー削除は confirm 後である
- **とき** 利用者が `/members` で、担当タスクの無いメンバーの削除を confirm する
- **ならば** そのメンバーはハード削除される
- **かつ** 一覧から消える

#### Scenario: confirm を拒否するとメンバーは残る
- **とき** 利用者が `/members` で削除を始め、confirm を拒否する
- **ならば** メンバーは残る

### Requirement: API は一段目のパスだけである
システムが提供する API は、GET と POST の `/api/members`、DELETE の `/api/members/{id}`、GET と POST の `/api/tasks`、GET と DELETE の `/api/tasks/{id}` だけであることが必須である。PATCH を提供してはならない。絞り込み用の API を提供してはならない。これ以外のパスを作ってはならない。

#### Scenario: 一覧と作成と詳細と削除だけがある
- **とき** クライアントが上記のパスを所定のメソッドで呼ぶ
- **ならば** その操作は契約どおりの結果を返す
- **かつ** PATCH のパスは無い

### Requirement: 作成は 201、削除は 204、不在は 404、検証失敗は 422 である
メンバー作成とタスク作成の成功は 201 で必須である。メンバー削除とタスク削除の成功は 204 で必須である。存在しないタスクの GET と、存在しないメンバーまたはタスクの DELETE は 404 で必須である。検証失敗は 422 で必須である。検証失敗のときストアを変えてはならない。空の一覧 GET は 200 と空配列で必須である。

#### Scenario: 作成と削除の成功
- **とき** クライアントが妥当なメンバーまたはタスクを作成し、そのあと存在する対象を削除する
- **ならば** 作成の応答は 201 である
- **かつ** 削除の応答は 204 である

#### Scenario: 対象が無い
- **とき** クライアントが存在しない id でタスクを GET する、または存在しない id でメンバーかタスクを DELETE する
- **ならば** 応答は 404 である
- **かつ** ストアは変わらない

#### Scenario: 検証失敗はストアを変えない
- **とき** クライアントが検証に失敗する作成または削除を送る
- **ならば** 応答は 422 である
- **かつ** ストアの件数と中身は変わらない

### Requirement: メンバー項目は id、name、createdAt である
システムは各メンバーを JSON の camelCase で表し、項目は `id`（UUID）、`name`、`createdAt` だけであることが必須である。`id` と `createdAt` はサーバが付与することが必須である。`createdAt` は UTC の ISO8601 で必須である。クライアントが送った `id` と `createdAt` を採用してはならない。保存する `name` は strip 後の値で必須である。

#### Scenario: 作成したメンバーは所定の項目を返す
- **とき** クライアントが名前でメンバーを作成する
- **ならば** 応答は `id`、`name`、`createdAt` を含む
- **かつ** `createdAt` は UTC の ISO8601 である
- **かつ** クライアントが `id` を送っても、保存される `id` はサーバの UUID である

### Requirement: タスク項目は id、title、assigneeId、done、createdAt である
システムは各タスクを JSON の camelCase で表し、項目は `id`（UUID）、`title`、`assigneeId`、`done`、`createdAt` だけであることが必須である。タスク JSON に `name` を持ってはならない。`id` と `createdAt` はサーバが付与することが必須である。`createdAt` は UTC の ISO8601 で必須である。保存する `title` は strip 後の値で必須である。GET（一覧・詳細）はこれら 5 キーだけを返すことが必須である。

#### Scenario: 作成したタスクは所定の項目を返す
- **とき** クライアントがタイトルでタスクを作成する
- **ならば** 応答は `id`、`title`、`assigneeId`、`done`、`createdAt` を含む
- **かつ** `name` という項目は存在しない
- **かつ** `createdAt` は UTC の ISO8601 である

### Requirement: name と title は strip 後に空なら 422 である
`name` は strip 後に空なら 422 で必須である。`title` は strip 後に空なら 422 で必須である。省略も 422 で必須である。同名のメンバーは許すことが必須である。

#### Scenario: 空の名前は拒否する
- **とき** クライアントが空、または空白だけの `name` でメンバーを作成する
- **ならば** 応答は 422 である
- **かつ** メンバーは増えない

#### Scenario: 空のタイトルは拒否する
- **とき** クライアントが空、または空白だけの `title` でタスクを作成する
- **ならば** 応答は 422 である
- **かつ** タスクは増えない

#### Scenario: 同名メンバーは許す
- **とき** クライアントが同じ `name` のメンバーを 2 人作成する
- **ならば** 両方とも 201 である
- **かつ** `id` は互いに異なる

### Requirement: タスク POST の assigneeId と done は採用しない
タスク作成でクライアントが送った `assigneeId` を採用してはならない。保存する担当者はサーバが決めることが必須である。クライアントが送った `done` を採用してはならない。一段目の保存値は false で必須である。

#### Scenario: クライアントの担当者と完了は捨てる
- **とき** クライアントが `assigneeId` と `done` が true のタスク作成を送る
- **ならば** 応答は 201 である
- **かつ** 保存された `assigneeId` はサーバが決めたメンバーである
- **かつ** 保存された `done` は false である

### Requirement: 担当者は未完了が最少のメンバーである
割り当ては、未完了（`done` が false）のタスクが最も少ないメンバーで必須である。同数なら `createdAt` が古いメンバーで必須である。`createdAt` も同じなら、`id` の辞書順が先のメンバーで必須である。一段目では完了を切り替えないため、未完了の件数は、そのメンバーを担当者にするタスクの件数と同じである。

#### Scenario: 未完了が少ないメンバーに割り当てる
- **とき** メンバーが 2 人おり、一方だけが未完了タスクを持っている状態でタスクを作成する
- **ならば** 保存される `assigneeId` は、未完了タスクが少ない方のメンバーである

#### Scenario: 同数なら古いメンバーに割り当てる
- **とき** メンバーが 2 人おり、未完了タスクの件数が同じ状態でタスクを作成する
- **ならば** 保存される `assigneeId` は、`createdAt` が古い方のメンバーである

#### Scenario: 作成日時も同じなら id が先のメンバーである
- **とき** 未完了タスクの件数と `createdAt` が同じメンバーが 2 人いる状態でタスクを作成する
- **ならば** 保存される `assigneeId` は、`id` の辞書順が先のメンバーである

### Requirement: メンバーが 0 人のタスク登録は 422 である
メンバーが 0 人のときのタスク作成は 422 で必須である。ストアを変えてはならない。

#### Scenario: メンバーがいないとタスクは作れない
- **とき** メンバーが 0 人の状態でタスクを作成する
- **ならば** 応答は 422 である
- **かつ** タスクは増えない
- **かつ** メンバーは増えない

### Requirement: 担当タスクが残るメンバー削除は 422 である
そのメンバーを `assigneeId` に持つタスクが 1 件でもある DELETE は 422 で必須である。カスケードしてはならない。担当タスクが無いメンバーの DELETE は 204 で必須である。存在しないメンバーの DELETE は 404 で必須である。

#### Scenario: 担当タスクが残ると削除できない
- **とき** クライアントが、担当タスクが 1 件以上あるメンバーを削除する
- **ならば** 応答は 422 である
- **かつ** そのメンバーは残る
- **かつ** そのタスクも残る

#### Scenario: 担当タスクが無いメンバーは削除できる
- **とき** クライアントが、担当タスクが無いメンバーを削除する
- **ならば** 応答は 204 である
- **かつ** そのメンバーの GET 一覧にその id は無い

### Requirement: タスク削除はハード削除である
存在するタスクの DELETE は 204 で必須である。削除後の GET は 404 で必須である。他のタスクの担当者を変えてはならない。存在しないタスクの DELETE は 404 で必須である。

#### Scenario: 削除したタスクは残らない
- **とき** クライアントが存在するタスクを削除する
- **ならば** 応答は 204 である
- **かつ** 同じ id の GET は 404 である
- **かつ** 他のタスクの `assigneeId` は変わらない

### Requirement: 一覧は createdAt 降順である
メンバー一覧とタスク一覧は `createdAt` の降順で必須である。同じ `createdAt` のときは `id` の辞書順が先のものを上にすることが必須である。

#### Scenario: タスク一覧は新しい方が上である
- **とき** 作成日時が異なるタスクが 2 件ある状態でタスク一覧を GET する
- **ならば** 応答は 200 である
- **かつ** 先頭は `createdAt` が新しいタスクである

#### Scenario: メンバー一覧は新しい方が上である
- **とき** 作成日時が異なるメンバーが 2 人いる状態でメンバー一覧を GET する
- **ならば** 応答は 200 である
- **かつ** 先頭は `createdAt` が新しいメンバーである

### Requirement: 担当者名は画面が結ぶ
画面に出す担当者名は、タスクの `assigneeId` と GET `/api/members` の `name` を画面で結んだ値で必須である。タスク API の JSON に `name` を足してはならない。

#### Scenario: 一覧と詳細に担当者名が出る
- **とき** メンバーが登録され、そのメンバーに割り当てられたタスクがある状態で一覧と詳細を開く
- **ならば** 担当者名としてそのメンバーの `name` が出る
- **かつ** タスク API の応答に `name` は無い

### Requirement: 両方未設定のときだけメモリである
`MEMBERS_TABLE` と `TASKS_TABLE` が両方未設定のとき、保存先はプロセス内メモリで必須である。再読み込み後も、そのプロセスが生きているあいだは残ることが必須である。片方だけ設定されているときは、起動を失敗させることが必須である。両方が設定されているときは、本番の保存先は DynamoDB で必須である。各テーブルの PK は `id` で必須である。一覧の取得は Scan で必須である。

#### Scenario: 両方未設定ならメモリに残る
- **とき** 両方の環境変数が未設定のプロセスでメンバーとタスクを作成し、同じプロセスに一覧を問い合わせる
- **ならば** 作成した内容が返る

#### Scenario: 片方だけでは起動しない
- **とき** `MEMBERS_TABLE` と `TASKS_TABLE` の片方だけが設定された状態でプロセスを起動する
- **ならば** 起動は失敗する
- **かつ** リクエストを受け付けない

### Requirement: 一段目では絞り込みと担当者変更と完了切替をしない
メンバー絞り込みを実装してはならない。担当者変更を実装してはならない。完了の切り替えを実装してはならない。タスクの `done` を false 以外に変える手段を提供してはならない。

#### Scenario: 一覧は全員のタスクである
- **とき** 担当者が異なるタスクが複数ある状態で `/` を開く
- **ならば** 絞り込みの操作は無い
- **かつ** 全部のタスクが出る

#### Scenario: 完了は false のままである
- **とき** 利用者が一段目の画面と API だけでタスクを操作する
- **ならば** 保存されている `done` は false のままである

### Requirement: タスク一覧からメンバー画面へ進める
システムは画面 `/` に、`/members` へ進む導線を必須で置く。この導線はタスク登録への導線とは別に置くことが必須である。URL を直接打つことだけを、メンバー画面への到達手段にしてはならない。

#### Scenario: 一覧の導線からメンバー画面を開く
- **とき** 利用者が `/` を開く
- **ならば** メンバー画面への導線がある
- **かつ** その導線はタスク登録への導線とは別である
- **かつ** その導線から `/members` を開ける
- **かつ** URL の直接入力だけが到達手段ではない

### Requirement: 一段目の完了表示は未完了である
一覧と詳細に出す完了の文言は「未完了」で必須である。保存値は false のままであることが必須である。完了の切り替えを足してはならない。

#### Scenario: 一覧と詳細は未完了と出す
- **とき** タスクがある状態で一覧と詳細を開く
- **ならば** 完了の文言は「未完了」である
- **かつ** 完了を切り替える操作は無い
- **かつ** 保存されている `done` は false である

### Requirement: 空のメンバー名は画面で登録できない
`/members` で名前が空、または空白だけのまま登録しようとしたとき、メンバーは増えないことが必須である。名前が必須であることが画面で分かることが必須である。API の 422 と、そのときのストア不変は、空の `name` の既存契約のままである。

#### Scenario: 空の名前では画面から増えない
- **とき** 利用者が `/members` で名前が空、または空白だけのまま登録しようとする
- **ならば** メンバーは増えない
- **かつ** 名前が必須であることが分かる

### Requirement: 設計図は CDK だけである
設計図は `infra/` の CDK（TypeScript）だけであることが必須である。スタック名は `AiDemo7ApiStack` であることが必須である。SAM の `template.yaml` を作ってはならない。

#### Scenario: SAM の設計図は無い
- **とき** この change の設計図を確認する
- **ならば** 設計図は `infra/` の CDK（TypeScript）である
- **かつ** スタック名は `AiDemo7ApiStack` である
- **かつ** `template.yaml` は無い

### Requirement: HttpApi は一段目のルートだけである
HttpApi のステージは `$default` であることが必須である。URL に `/prod` を付けてはならない。Mangum に `api_gateway_base_path` を付けてはならない。Lambda に繋ぐルートを `$default` にしてはならない。Lambda ルートは GET/POST `/api/members`、DELETE `/api/members/{id}`、GET/POST `/api/tasks`、GET/DELETE `/api/tasks/{id}` だけであることが必須である。PATCH ルートを作ってはならない。OPTIONS は API Gateway の corsPreflight に残すことが必須である。本番 CORS の許可オリジンは `*` であることが必須である。メソッドは GET、POST、DELETE、OPTIONS であることが必須である。Lambda Timeout は 15 秒であることが必須である。CORS を FastAPI に足してはならない。ローカルは Vite が `/api` を `http://127.0.0.1:8000` へプロキシすることが必須である。

#### Scenario: Lambda ルートは一段目だけである
- **とき** HttpApi の Lambda ルートを確認する
- **ならば** ルートは GET/POST `/api/members`、DELETE `/api/members/{id}`、GET/POST `/api/tasks`、GET/DELETE `/api/tasks/{id}` だけである
- **かつ** PATCH ルートは無い
- **かつ** Lambda に繋ぐ `$default` ルートは無い
- **かつ** OPTIONS は corsPreflight にある
- **かつ** ステージは `$default` であり、URL に `/prod` は無い
- **かつ** Timeout は 15 秒である
- **かつ** 許可オリジンは `*` であり、メソッドは GET、POST、DELETE、OPTIONS である
- **かつ** Mangum に `api_gateway_base_path` は無い
- **かつ** FastAPI に CORS は無い

#### Scenario: ローカルは Vite がプロキシする
- **とき** ローカルの画面が API を呼ぶ
- **ならば** Vite が `/api` を `http://127.0.0.1:8000` へプロキシする

### Requirement: DynamoDB は 2 テーブルである
DynamoDB は 2 テーブルであることが必須である。名前は `${stackName}-members` と `${stackName}-tasks` であることが必須である。PK は `id` であることが必須である。一覧は Scan であることが必須である。GSI を足してはならない。環境変数は `MEMBERS_TABLE` と `TASKS_TABLE` であることが必須である。

#### Scenario: テーブルは 2 つで GSI は無い
- **とき** データ用の AWS 資源を確認する
- **ならば** テーブル名は `${stackName}-members` と `${stackName}-tasks` である
- **かつ** PK は `id` である
- **かつ** 一覧は Scan である
- **かつ** GSI は無い
- **かつ** 環境変数は `MEMBERS_TABLE` と `TASKS_TABLE` である

### Requirement: フロント配信は S3 と CloudFront である
フロント配信は S3 と CloudFront（OAC。403 と 404 は `index.html`）であることが必須である。`BucketDeployment` をしてはならない。CDK Output は `ApiUrl`、`FrontendUrl`、`FrontendBucketName`、`CloudFrontDistributionId` だけであることが必須である。足してよい AWS は Lambda、API Gateway、DynamoDB、IAM ロール、CloudWatch Logs、S3、CloudFront だけである。`infra/bin/infra.ts` は、Docker が無い `cdk deploy` を例外で止めることが必須である。`cdk synth` で Docker が無いときだけ bundling を無効化してよい。`cdk deploy` はこの change では実行してはならない。

#### Scenario: Output は 4 つだけである
- **とき** CDK の Output と配信資源を確認する
- **ならば** 配信は S3 と CloudFront（OAC。403 と 404 は `index.html`）である
- **かつ** `BucketDeployment` は無い
- **かつ** Output は `ApiUrl`、`FrontendUrl`、`FrontendBucketName`、`CloudFrontDistributionId` だけである
- **かつ** 宣言されている AWS は Lambda、API Gateway、DynamoDB、IAM ロール、CloudWatch Logs、S3、CloudFront だけである

#### Scenario: Docker が無いデプロイは止まる
- **とき** Docker が無い状態で `cdk deploy` を実行しようとする
- **ならば** `infra/bin/infra.ts` が例外で止める
- **かつ** この change では `cdk deploy` を実行しない

#### Scenario: synth だけ bundling を外してよい
- **とき** Docker が無い状態で `cdk synth` を実行する
- **ならば** bundling の無効化は許される
- **かつ** その無効化を `cdk deploy` には使わない

### Requirement: 画面の合否は Playwright Test である
画面の合否は `frontend/e2e/` の Playwright Test であることが必須である。ブラウザは Chromium だけであることが必須である。サーバの 422 は backend の pytest が正であることが必須である。e2e に 422 を足してはならない。リポジトリ直下の `playwright.config.ts` と `tests/example.spec.ts` は初期化の見本である。合否に使ってはならない。見本の設定を `frontend/` へ移してはならない。見本を消してはならない。Playwright MCP は下書きである。合否にしてはならない。

#### Scenario: 合否は Chromium の e2e である
- **とき** 画面の合否を確認する
- **ならば** 実行場所は `frontend/e2e/` である
- **かつ** ブラウザは Chromium だけである
- **かつ** サーバの 422 は pytest が正である
- **かつ** e2e に 422 は無い

#### Scenario: 見本と MCP は合否ではない
- **とき** リポジトリ直下の見本と Playwright MCP を確認する
- **ならば** 見本は合否に使っていない
- **かつ** 見本の設定は `frontend/` に移していない
- **かつ** 見本は残っている
- **かつ** Playwright MCP は合否ではない
