## MODIFIED Requirements

### Requirement: タスク一覧は / である
システムは画面 `/` でタスク一覧を必須で出す。並びは `createdAt` の降順で必須である。各項目は担当者名、完了、作成日時を必須で示す。カードからそのタスクの詳細 `/tasks/:id` へ必須で遷移する。タスクが無いときは、タスクが無いことが分かる表示で必須である。タスク登録への導線は必須である。完了済みのタスクも一覧に残すことが必須である。一覧に削除を置いてはならない。メンバー絞り込みを置いてはならない。完了の切り替えを置いてはならない。担当者の変更を置いてはならない。

#### Scenario: 空のタスク一覧
- **とき** タスクがまだ無い状態で `/` を開く
- **ならば** タスクが無いことが分かる
- **かつ** タスク登録への導線がある
- **かつ** 削除操作は無い

#### Scenario: 一覧は新しいタスクが上である
- **とき** 作成日時が異なるタスクが 2 件以上ある状態で `/` を開く
- **ならば** `createdAt` が新しいタスクが上に出る
- **かつ** 各項目に担当者名、完了、作成日時が出る
- **かつ** カードからそのタスクの詳細へ遷移できる
- **かつ** 一覧に削除は無い

#### Scenario: 完了済みも一覧に残る
- **とき** `done` が true のタスクと false のタスクがある状態で `/` を開く
- **ならば** 両方とも一覧に出る
- **かつ** 一覧に完了の切り替えは無い
- **かつ** 一覧に担当者の変更は無い

### Requirement: タスク詳細は /tasks/:id である
システムは画面 `/tasks/:id` で、そのタスクのタイトル、担当者名、完了、作成日時を必須で出す。削除は confirm のあとだけ実行することが必須である。削除に成功したならば `/` へ必須で戻る。存在しない id は、見つからないことが分かる表示で必須である。担当者を、存在するメンバーの中から選んで変えられることが必須である。完了を切り替えられることが必須である。候補に、存在しないメンバーを出してはならない。一覧に担当者の変更と完了の切り替えを置いてはならない。

#### Scenario: 詳細を見て confirm 後に削除する
- **とき** 利用者が存在するタスクの詳細を開き、削除を confirm する
- **ならば** そのタスクはハード削除される
- **かつ** `/` へ戻る
- **かつ** 一覧にそのタスクは無い

#### Scenario: confirm を拒否すると削除されない
- **とき** 利用者が詳細で削除を始め、confirm を拒否する
- **ならば** タスクは残る
- **かつ** 画面は詳細のままである

#### Scenario: 存在しないタスクは見つからない
- **とき** 利用者が存在しない id の `/tasks/:id` を開く
- **ならば** 見つからないことが分かる

#### Scenario: 詳細に担当者変更と完了切替は無い
- **とき** 利用者がタスク詳細を見る
- **ならば** 担当者を変える操作がある
- **かつ** 完了を切り替える操作がある
- **かつ** その候補は存在するメンバーだけである

#### Scenario: 詳細で担当者を変える
- **とき** 利用者が詳細で、別の存在するメンバーを担当者に選ぶ
- **ならば** そのタスクの担当者名は選んだメンバーになる
- **かつ** 他のタスクの担当者は変わらない

#### Scenario: 詳細で完了を切り替える
- **とき** 利用者が詳細で完了を切り替える
- **ならば** そのタスクの完了の文言が切り替わる
- **かつ** 一覧に戻ってもそのタスクは残る
- **かつ** 一覧に完了の切り替えは無い

### Requirement: API は一段目のパスだけである
システムが提供する API は、GET と POST の `/api/members`、DELETE の `/api/members/{id}`、GET と POST の `/api/tasks`、GET と DELETE と PATCH の `/api/tasks/{id}` だけであることが必須である。絞り込み用の API を提供してはならない。これ以外のパスを作ってはならない。

#### Scenario: 一覧と作成と詳細と削除だけがある
- **とき** クライアントが上記のパスを所定のメソッドで呼ぶ
- **ならば** その操作は契約どおりの結果を返す
- **かつ** PATCH は `/api/tasks/{id}` だけである
- **かつ** 絞り込み用の API は無い

### Requirement: 担当者は未完了が最少のメンバーである
タスク作成の割り当ては、未完了（`done` が false）のタスクが最も少ないメンバーで必須である。同数なら `createdAt` が古いメンバーで必須である。`createdAt` も同じなら、`id` の辞書順が先のメンバーで必須である。未完了の件数に、`done` が true のタスクを入れてはならない。この割り当てはタスク作成のときだけ行うことが必須である。PATCH で他のタスクを再割り当てしてはならない。

#### Scenario: 未完了が少ないメンバーに割り当てる
- **とき** メンバーが 2 人おり、一方だけが未完了タスクを持っている状態でタスクを作成する
- **ならば** 保存される `assigneeId` は、未完了タスクが少ない方のメンバーである

#### Scenario: 同数なら古いメンバーに割り当てる
- **とき** メンバーが 2 人おり、未完了タスクの件数が同じ状態でタスクを作成する
- **ならば** 保存される `assigneeId` は、`createdAt` が古い方のメンバーである

#### Scenario: 作成日時も同じなら id が先のメンバーである
- **とき** 未完了タスクの件数と `createdAt` が同じメンバーが 2 人いる状態でタスクを作成する
- **ならば** 保存される `assigneeId` は、`id` の辞書順が先のメンバーである

#### Scenario: 完了済みは未完了の件数に入れない
- **とき** メンバーが 2 人おり、一方は未完了タスクが 1 件、もう一方は担当タスクが 1 件だが `done` が true である状態でタスクを作成する
- **ならば** 保存される `assigneeId` は、`done` が true のタスクだけを持つメンバーである
- **かつ** 既存タスクの担当者は変わらない

### Requirement: 一段目では絞り込みと担当者変更と完了切替をしない
メンバー絞り込みを実装してはならない。担当者変更と完了の切り替えは、詳細画面と `PATCH /api/tasks/{id}` だけで行うことが必須である。一覧に担当者の変更と完了の切り替えを置いてはならない。タスク POST の `done` は false のままであることが必須である。

#### Scenario: 一覧は全員のタスクである
- **とき** 担当者が異なるタスクが複数あり、その中に完了済みがある状態で `/` を開く
- **ならば** 絞り込みの操作は無い
- **かつ** 全部のタスクが出る
- **かつ** 完了済みも出る

#### Scenario: 完了は false のままである
- **とき** クライアントがタスクを POST する
- **ならば** 保存された `done` は false である
- **かつ** 詳細と PATCH で切り替えていないタスクの `done` は false のままである

### Requirement: 一段目の完了表示は未完了である
一覧と詳細に出す完了の文言は、`done` が true なら「完了」、false なら「未完了」で必須である。一覧と詳細の両方であることが必須である。完了済みのタスクも一覧に残すことが必須である。一覧に完了の切り替えを置いてはならない。

#### Scenario: 一覧と詳細は未完了と出す
- **とき** `done` が false のタスクがある状態で一覧と詳細を開く
- **ならば** 完了の文言は「未完了」である
- **かつ** 一覧に完了の切り替えは無い

#### Scenario: 一覧と詳細は完了と出す
- **とき** `done` が true のタスクがある状態で一覧と詳細を開く
- **ならば** 完了の文言は「完了」である
- **かつ** そのタスクは一覧に残る
- **かつ** 一覧に完了の切り替えは無い

### Requirement: HttpApi は一段目のルートだけである
HttpApi のステージは `$default` であることが必須である。URL に `/prod` を付けてはならない。Mangum に `api_gateway_base_path` を付けてはならない。Lambda に繋ぐルートを `$default` にしてはならない。Lambda ルートは GET/POST `/api/members`、DELETE `/api/members/{id}`、GET/POST `/api/tasks`、GET/DELETE/PATCH `/api/tasks/{id}` だけであることが必須である。これ以外の Lambda ルートを足してはならない。OPTIONS は API Gateway の corsPreflight に残すことが必須である。本番 CORS の許可オリジンは `*` であることが必須である。メソッドは GET、POST、DELETE、PATCH、OPTIONS であることが必須である。Lambda Timeout は 15 秒であることが必須である。CORS を FastAPI に足してはならない。ローカルは Vite が `/api` を `http://127.0.0.1:8000` へプロキシすることが必須である。新しい AWS サービスを足してはならない。スタック名、テーブル、Output は一段目のままであることが必須である。

#### Scenario: Lambda ルートは一段目だけである
- **とき** HttpApi の Lambda ルートを確認する
- **ならば** ルートは GET/POST `/api/members`、DELETE `/api/members/{id}`、GET/POST `/api/tasks`、GET/DELETE/PATCH `/api/tasks/{id}` だけである
- **かつ** Lambda に繋ぐ `$default` ルートは無い
- **かつ** OPTIONS は corsPreflight にある
- **かつ** ステージは `$default` であり、URL に `/prod` は無い
- **かつ** Timeout は 15 秒である
- **かつ** 許可オリジンは `*` であり、メソッドは GET、POST、DELETE、PATCH、OPTIONS である
- **かつ** Mangum に `api_gateway_base_path` は無い
- **かつ** FastAPI に CORS は無い
- **かつ** 新しい AWS サービスは無い
- **かつ** スタック名、テーブル、Output は一段目のままである

#### Scenario: ローカルは Vite がプロキシする
- **とき** ローカルの画面が API を呼ぶ
- **ならば** Vite が `/api` を `http://127.0.0.1:8000` へプロキシする

### Requirement: 画面の合否は Playwright Test である
画面の合否は `frontend/e2e/` の Playwright Test であることが必須である。ブラウザは Chromium だけであることが必須である。サーバの 422 と 404 は backend の pytest が正であることが必須である。e2e に 422 を足してはならない。e2e は、担当者変更、完了の切り替え、文言「完了」と「未完了」、完了済みが一覧に残ることを断言することが必須である。リポジトリ直下の `playwright.config.ts` と `tests/example.spec.ts` は初期化の見本である。合否に使ってはならない。見本の設定を `frontend/` へ移してはならない。見本を消してはならない。Playwright MCP は下書きである。合否にしてはならない。

#### Scenario: 合否は Chromium の e2e である
- **とき** 画面の合否を確認する
- **ならば** 実行場所は `frontend/e2e/` である
- **かつ** ブラウザは Chromium だけである
- **かつ** サーバの 422 と 404 は pytest が正である
- **かつ** e2e に 422 は無い

#### Scenario: 見本と MCP は合否ではない
- **とき** リポジトリ直下の見本と Playwright MCP を確認する
- **ならば** 見本は合否に使っていない
- **かつ** 見本の設定は `frontend/` に移していない
- **かつ** 見本は残っている
- **かつ** Playwright MCP は合否ではない

#### Scenario: e2e は担当者変更と完了切替を断言する
- **とき** `frontend/e2e/` の Playwright Test を確認する
- **ならば** 担当者の変更が断言されている
- **かつ** 完了の切り替えが断言されている
- **かつ** 文言「完了」と「未完了」が断言されている
- **かつ** 完了済みが一覧に残ることが断言されている

## ADDED Requirements

### Requirement: PATCH はそのタスクの assigneeId と done だけを変える
`PATCH /api/tasks/{id}` は、送った `assigneeId` と `done` だけを、そのタスクについて変えることが必須である。片方だけでも更新できることが必須である。両方省略は 422 で必須である。空、または空白だけの `assigneeId` は 422 で必須である。存在しないメンバーへの `assigneeId` は 422 で必須である。boolean でない `done` は 422 で必須である。`assigneeId` と `done` の片方が検証失敗のとき、もう片方が妥当でも 422 で必須である。422 のときストアを変えてはならない。存在しないタスクは、本文の検証より先に 404 で必須である。`id`、`createdAt`、`title` は不変で必須である。PATCH にこれらが付いていても捨て、422 にはしないことが必須である。保存値は変えてはならない。他のタスクを再割り当てしてはならない。存在しないタスクの PATCH は 404 で必須である。404 のときストアを変えてはならない。成功は 200 で必須である。応答は `id`、`title`、`assigneeId`、`done`、`createdAt` の 5 キーだけであることが必須である。タスク JSON に `name` を足してはならない。タスク POST の `assigneeId` と `done` は採用してはならない。新規の `done` は false のままであることが必須である。

#### Scenario: assigneeId だけを更新する
- **とき** クライアントが存在するタスクへ、存在するメンバーの `assigneeId` だけを PATCH する
- **ならば** 応答は 200 である
- **かつ** そのタスクの `assigneeId` は送った値である
- **かつ** そのタスクの `done`、`id`、`title`、`createdAt` は変わらない
- **かつ** 他のタスクの `assigneeId` と `done` は変わらない

#### Scenario: done だけを更新する
- **とき** クライアントが存在するタスクへ、boolean の `done` だけを PATCH する
- **ならば** 応答は 200 である
- **かつ** そのタスクの `done` は送った値である
- **かつ** そのタスクの `assigneeId`、`id`、`title`、`createdAt` は変わらない
- **かつ** 他のタスクは再割り当てされない

#### Scenario: 両方省略は拒否する
- **とき** クライアントが存在するタスクへ、`assigneeId` も `done` も無い PATCH を送る
- **ならば** 応答は 422 である
- **かつ** ストアは変わらない

#### Scenario: 空の担当者は拒否する
- **とき** クライアントが空、または空白だけの `assigneeId` で PATCH する
- **ならば** 応答は 422 である
- **かつ** ストアは変わらない

#### Scenario: 存在しないメンバーは拒否する
- **とき** クライアントが、存在しないメンバーの `assigneeId` で PATCH する
- **ならば** 応答は 422 である
- **かつ** ストアは変わらない

#### Scenario: boolean でない完了は拒否する
- **とき** クライアントが boolean でない `done` で PATCH する
- **ならば** 応答は 422 である
- **かつ** ストアは変わらない

#### Scenario: id と createdAt と title は捨てる
- **とき** クライアントが、妥当な `assigneeId` または `done` に加えて `id`、`createdAt`、`title` を PATCH する
- **ならば** 応答は 422 ではない
- **かつ** 保存された `id`、`createdAt`、`title` は変わらない
- **かつ** 送った `assigneeId` または `done` だけが変わる

#### Scenario: 不変項目だけを送ると更新されない
- **とき** クライアントが存在するタスクへ、`id`、`createdAt`、`title` だけで PATCH する
- **ならば** 応答は 422 である
- **かつ** 保存値は変わらない

#### Scenario: 片方だけ不正でもストアは変わらない
- **とき** クライアントが、妥当な `done` と、存在しないメンバーの `assigneeId` を同じ PATCH で送る
- **ならば** 応答は 422 である
- **かつ** そのタスクの `done` も `assigneeId` も変わらない

#### Scenario: 存在しないタスクは 404 である
- **とき** クライアントが存在しない id のタスクを PATCH する
- **ならば** 応答は 404 である
- **かつ** ストアは変わらない

#### Scenario: 存在しないタスクは本文が不正でも 404 である
- **とき** クライアントが存在しない id へ、空の `assigneeId` で PATCH する
- **ならば** 応答は 404 である
- **かつ** ストアは変わらない

#### Scenario: 成功は 5 キーを返す
- **とき** クライアントが妥当な PATCH に成功する
- **ならば** 応答は 200 である
- **かつ** 応答は `id`、`title`、`assigneeId`、`done`、`createdAt` を含む
- **かつ** `name` という項目は存在しない

#### Scenario: タスク POST の担当者と完了は捨てたままである
- **とき** クライアントが `assigneeId` と `done` が true のタスク作成を送る
- **ならば** 応答は 201 である
- **かつ** 保存された `assigneeId` はサーバが決めたメンバーである
- **かつ** 保存された `done` は false である
