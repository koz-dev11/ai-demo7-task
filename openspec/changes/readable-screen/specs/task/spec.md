## ADDED Requirements

### Requirement: タスクを登録は登録ボタンと同じ見た目のリンクである
「タスクを登録」は `/` のナビゲーションの中にあることが必須である。順は「メンバー」、その次が「タスクを登録」であることが必須である。文言と `/new` へのリンクは変えてはならない。画面右下に固定してはならない。固定のための一覧下の余白を置いてはならない。見た目は、登録ボタンと同じ黒地・白文字であることが必須である。要素はリンクのままであることが必須である。class `register-link` を使ってはならない。

#### Scenario: タスクを登録は黒地のリンクである
- **とき** `/` を開く
- **ならば** 「タスクを登録」はナビゲーションの中のリンクである
- **かつ** そのリンク先は `/new` である
- **かつ** 「メンバー」はその前にある
- **かつ** 背景は登録ボタンと同じ黒で、文字は白である
- **かつ** 画面右下には固定されていない
- **かつ** 一覧の下に、固定のための余白は無い
- **かつ** class `register-link` は無い

## MODIFIED Requirements

### Requirement: 一覧のカードは2段の塊である
画面 `/` の各タスクは、枠と余白を持つ塊であることが必須である。中の基本は 2 段であることが必須である。1 段目はタイトルだけを、他の文字より大きく出すことが必須である。2 段目は担当者名、「完了」または「未完了」、作成日時を、1 段目より小さく横に並べることが必須である。作成日時は UTC ISO8601 の文字のまま、小さい灰色であり、その行の右端に寄せることが必須である。`dueOn`、`completedAt` があるとき、および期限超過のときは、それらをカードの中の、2 段目とは別の行に出すことが必須である。その行の項目のあいだには間隔を置くことが必須である。日付、「完了日」、「期限超過」を隙間なくつなげてはならない。期限の表示は `YYYY-MM-DD` のままであることが必須である。一覧に「期限」というラベルを足してはならない。`body` の全文をカードに出してはならない。箇条書きの黒丸を出してはならない。カードのリンクの中に、タイトル、担当者名、完了の文言、作成日時の文字が入っていることが必須である。一覧に削除、担当者の select、完了の checkbox を置いてはならない。期限超過のカードは、左の線を `#b45309` にすることが必須である。カードの中に「期限超過」と出すことが必須である。「期限超過」の文字色も `#b45309` であることが必須である。色だけにしてはならない。

#### Scenario: カードは2段で黒丸が無い
- **とき** タスクが 1 件以上ある状態で `/` を開く
- **ならば** 各タスクは枠と余白のある塊である
- **かつ** 1 段目はタイトルだけが大きく出る
- **かつ** 2 段目に担当者名、完了の文言、作成日時が小さく横に並ぶ
- **かつ** 作成日時は UTC ISO8601 の小さい灰色で、その行の右端にある
- **かつ** 箇条書きの黒丸は無い
- **かつ** それらの文字は、そのタスクの詳細へ進むリンクの中にある
- **かつ** 一覧に削除、担当者の select、完了の checkbox は無い
- **かつ** `body` の全文は一覧に出ない

#### Scenario: 期限と完了日は間隔を置く
- **とき** `dueOn` と `completedAt` があるタスクを `/` で見る
- **ならば** その `YYYY-MM-DD` と「完了日」は、2 段目とは別の行にある
- **かつ** そのあいだに間隔がある
- **かつ** 一覧に「期限」というラベルは無い

#### Scenario: 期限だけの行にもラベルは無い
- **とき** `dueOn` があり、完了日も期限超過も無いタスクを `/` で見る
- **ならば** その `YYYY-MM-DD` は、2 段目とは別の行に出る
- **かつ** 一覧に「期限」というラベルは無い

#### Scenario: 期限超過は線と文言である
- **とき** `done` が false で、`dueOn` が利用者のローカル日付より前のタスクを `/` で見る
- **ならば** そのカードの左の線は `#b45309` である
- **かつ** カードの中に「期限超過」と出る
- **かつ** 「期限超過」の文字色は `#b45309` である
- **かつ** その `YYYY-MM-DD` と「期限超過」は、2 段目とは別の行にあり、あいだに間隔がある
- **かつ** 当日の期限、期限が無いタスク、完了済みのタスクには「期限超過」は出ない

### Requirement: メンバーの select はナビゲーションの下にある
画面 `/` の「メンバー」の select は、ナビゲーションの下に 1 行とって置くことが必須である。ラベルと select は横一列であることが必須である。この横並びで、`/new` と `/members` の登録フォームの縦積みを崩してはならない。ラベルは「メンバー」であることが必須である。先頭の表示は「全員」、値は空文字であることが必須である。続く選択肢の表示は `name`、値は `id` であることが必須である。絞り込みの仕様は変えてはならない。

#### Scenario: select はナビの下の1行である
- **とき** `/` を開く
- **ならば** 「メンバー」の select はナビゲーションの下に 1 行で出る
- **かつ** ラベルと select は横一列である
- **かつ** 先頭の表示は「全員」で、値は空文字である
- **かつ** 続く選択肢の表示は `name`、値は `id` である

### Requirement: 詳細はラベルが上で操作が下である
画面 `/tasks/:id` の欄は、上から、担当者、完了の行、期限、完了日、作成日時、内容、「削除」の順であることが必須である。完了日は、`completedAt` があるときだけ、期限の次に出すことが必須である。`completedAt` が null のときは、完了日を出さず、期限の次は作成日時であることが必須である。各項目はラベルを上、操作を下に置くことが必須である。欄と欄のあいだに余白を置くことが必須である。担当者名は、その select の選択中の表示だけであることが必須である。select の外に同じ名前を出してはならない。完了の文言と checkbox は同じ行に置くことが必須である。checkbox の名前「完了を切り替える」は変えてはならない。期限の入力は `type="date"` であることが必須である。詳細の日付欄を本文幅いっぱいに伸ばしてはならない。完了日をクライアントが入力する欄にしてはならない。完了日の文字の並びは、「完了日」のあとに空白を挟んで、その UTC ISO8601 であることが必須である。作成日時は UTC ISO8601 のまま、小さい灰色であることが必須である。作成日時に新しいラベルを足してはならない。内容は平文の `textarea` であることが必須である。最小の高さを持たせることが必須である。Markdown として描画してはならない。

#### Scenario: 完了日があるときの欄の順である
- **とき** `completedAt` があるタスクの詳細を開く
- **ならば** 上から、担当者、完了の行、期限、完了日、作成日時、内容、「削除」の順である
- **かつ** 各欄は、ラベルが上で、操作が下である
- **かつ** 欄と欄のあいだに余白がある

#### Scenario: 完了日が無いときの欄の順である
- **とき** `completedAt` が null のタスクの詳細を開く
- **ならば** 「完了日」は出ない
- **かつ** 上から、担当者、完了の行、期限、作成日時、内容、「削除」の順である

#### Scenario: 担当者はラベルが上である
- **とき** 存在するタスクの詳細を開く
- **ならば** 「担当者」のラベルは、その select の上にある
- **かつ** 担当者名は、その select の選択中に出る
- **かつ** select の外に同じ名前は出ない

#### Scenario: 完了の文言と checkbox は同じ行である
- **とき** 存在するタスクの詳細を開く
- **ならば** 「完了」または「未完了」と、checkbox が同じ行にある
- **かつ** checkbox の名前は「完了を切り替える」である

#### Scenario: 内容と期限はラベルが上である
- **とき** 存在するタスクの詳細を開く
- **ならば** 内容のラベルは、その入力の上にある
- **かつ** 期限のラベルは、その入力の上にある
- **かつ** 完了日の入力欄は無い

#### Scenario: 期限の日付欄は本文幅いっぱいではない
- **とき** 存在するタスクの詳細を開く
- **ならば** 「期限」のラベルは、`type="date"` の入力の上にある
- **かつ** その入力は本文幅いっぱいではない

#### Scenario: 完了日は空白を挟んだ文字である
- **とき** `completedAt` があるタスクの詳細を開く
- **ならば** 「完了日」のあとに空白があり、その次に UTC ISO8601 の文字がある
- **かつ** 完了日の入力欄は無い

#### Scenario: 作成日時に新しいラベルは無い
- **とき** 存在するタスクの詳細を開く
- **ならば** 作成日時は UTC ISO8601 の小さい灰色である
- **かつ** 作成日時のための新しいラベルは無い

#### Scenario: 内容は最小の高さの平文である
- **とき** 存在するタスクの詳細を開く
- **ならば** 内容のラベルは、その `textarea` の上にある
- **かつ** その `textarea` は最小の高さを持つ
- **かつ** 内容は平文である
- **かつ** Markdown としては描画されない

### Requirement: 削除は内容から離れ登録とは色が違う
「削除」は、その画面の内容から離して置くことが必須である。背景は `#9f1239`、文字は白であることが必須である。登録ボタンとは違う色であることが必須である。確認の文言「削除しますか？」は変えてはならない。

#### Scenario: 削除は離れていて色が違う
- **とき** 詳細、またはメンバー画面で「削除」を見る
- **ならば** 「削除」は内容から離れている
- **かつ** 背景は `#9f1239` である
- **かつ** 文字は白である
- **かつ** 「登録する」とは違う色である
- **かつ** 確認の文言は「削除しますか？」のままである

### Requirement: メンバーの1行は名前、日時、削除である
画面 `/members` の 1 行は、名前を左、作成日時を小さく、削除を右端に置くことが必須である。行のあいだを線で区切ることが必須である。箇条書きの黒丸を出してはならない。

#### Scenario: メンバー行は左右に分かれる
- **とき** メンバーが 1 人以上いる状態で `/members` を開く
- **ならば** 名前は左にある
- **かつ** 作成日時は小さい
- **かつ** 削除は右端にある
- **かつ** 行のあいだは線で区切られている
- **かつ** 箇条書きの黒丸は無い

### Requirement: 登録フォームは縦に積む
登録フォームは、ラベルを上、入力欄をその下に幅いっぱいで置き、ボタンをその下に置くことが必須である。エラーは入力欄の直下に置くことが必須である。欄と欄のあいだに余白を置くことが必須である。対象は `/new` と `/members` である。ラベル「タイトル」「名前」「内容」「期限」、ボタン「登録する」、エラー「タイトルは必須です」「名前は必須です」は変えてはならない。`/new` の内容と期限も、同じ縦の並びであることが必須である。内容の `textarea` は、詳細の内容と同じ最小の高さを持つことが必須である。絞り込みの横並びで、この縦積みを崩してはならない。

#### Scenario: 入力の直下にエラーが出る
- **とき** `/new` でタイトルが空のまま登録しようとする
- **ならば** ラベル「タイトル」は入力欄の上にある
- **かつ** 入力欄は幅いっぱいである
- **かつ** エラーは入力欄の直下にある
- **かつ** 「登録する」はその下にある
- **かつ** エラーの文言は「タイトルは必須です」のままである

#### Scenario: メンバー登録も同じ並びである
- **とき** `/members` で名前が空のまま登録しようとする
- **ならば** ラベル「名前」は入力欄の上にある
- **かつ** 入力欄は幅いっぱいである
- **かつ** エラーは入力欄の直下にある
- **かつ** 「登録する」はその下にある
- **かつ** エラーの文言は「名前は必須です」のままである

#### Scenario: 内容と期限も縦に積む
- **とき** `/new` を開く
- **ならば** 内容のラベルは、その入力の上にある
- **かつ** 期限のラベルは、その入力の上にある
- **かつ** 入力欄は幅いっぱいである
- **かつ** 欄と欄のあいだに余白がある
- **かつ** 「登録する」はそれらの下にある
- **かつ** 内容の `textarea` は、詳細の内容と同じ最小の高さを持つ

### Requirement: 見た目の合否は既存の e2e である
画面の合否は `frontend/e2e/board.spec.ts` の Playwright Test であることが必須である。ブラウザは Chromium だけであることが必須である。既存の断言を崩してはならない。見た目のための新しい screenshot テストを足してはならない。サーバの 422 と 404 は既存の pytest が正であることが必須である。e2e に 422 を足してはならない。内容、完了日、期限、期限超過、登録位置の断言は、同じ Playwright Test に残すことが必須である。

#### Scenario: screenshot テストは足さない
- **とき** 画面の合否を確認する
- **ならば** `frontend/e2e/board.spec.ts` を Chromium だけで実行する
- **かつ** 既存の断言は残っている
- **かつ** 見た目のための新しい screenshot テストは無い
- **かつ** e2e に 422 は無い
