## Purpose

認証なしの公開タスクボードとして、メンバーの登録・一覧・削除と、タスクの登録・一覧・詳細・削除を提供する。登録されたタスクの担当者はサーバが割り当てる。個人情報・社外秘は入れない。

## Requirements

### Requirement: 一段目は認証を要求しない
システムはログインを要求してはならない。`/login` を提供してはならない。誰でもメンバーとタスクを読み書き・削除できることが必須である。ユーザー識別情報は持ってはならない。

#### Scenario: 未ログインで操作できる
- **とき** 未ログインの利用者がメンバーの登録と、タスクの登録・一覧・詳細・削除を行う
- **ならば** 認証画面やログイン要求は出ない
- **かつ** 操作は完了する
### Requirement: 画面ルートは 4 つだけである
システムが提供する画面ルートは `/`、`/new`、`/tasks/:id`、`/members` だけであることが必須である。`/login` と `/members/:id` を足してはならない。未知のパスは、見つからないことが分かる表示で必須である。

#### Scenario: 未知のパスは見つからない
- **とき** 利用者が `/login` または `/members/anything` またはその他の未知パスを開く
- **ならば** 見つからないことが分かる
- **かつ** メンバー一覧やタスク一覧としては扱わない
### Requirement: タスク一覧は / である
システムは画面 `/` でタスク一覧を必須で出す。並びは `createdAt` の降順で必須である。絞り込みのあとでも、その順のままであることが必須である。各項目は担当者名、完了、作成日時を必須で示す。`dueOn` があるときは、その `YYYY-MM-DD` をカードの中に出すことが必須である。`completedAt` があるときは、「完了日」と、その UTC ISO8601 の文字をカードの中に出すことが必須である。`completedAt` が null のときは「完了日」を出してはならない。`body` の全文を一覧に出してはならない。カードからそのタスクの詳細 `/tasks/:id` へ必須で遷移する。タスクが無いとき、および絞った結果が 0 件のときは、タスクが無いことが分かる表示のままであることが必須である。そのときも select は残すことが必須である。タスク登録への導線は必須である。「タスクを登録」は `/` のナビゲーションの中にあることが必須である。画面右下に固定してはならない。文言と `/new` へのリンクは変えてはならない。「メンバー」も同じナビゲーションに残すことが必須である。順は「メンバー」、その次が「タスクを登録」であることが必須である。固定ボタンのための余白を一覧の下に置いてはならない。完了済みのタスクも、絞り込みの対象に入るなら一覧に残すことが必須である。一覧に削除を置いてはならない。完了の切り替えを置いてはならない。担当者の変更を置いてはならない。一覧をメンバーで絞る select を置くことが必須である。初期選択は「全員」であることが必須である。「全員」の値はメンバーの `id` ではないことが必須である。続く選択肢は GET `/api/members` のメンバーであることが必須である。表示は `name`、値は `id` であることが必須である。並びは API の順であることが必須である。同名でも `id` で区別することが必須である。「全員」のときは全件を出すことが必須である。1 人を選んだときは、その `id` と `assigneeId` が一致するタスクだけを出すことが必須である。絞り込みは、既存の GET `/api/tasks` 全件に対する画面の処理であることが必須である。新しい API、別の一覧 API、クエリ付きの GET を足してはならない。URL に絞り込みを載せてはならない。`/` を開いたとき、および詳細から一覧へ戻ったときの初期値は「全員」であることが必須である。選んだ `id` のメンバーが無いときは「全員」に戻すことが必須である。期限超過は、`done` が false で、`dueOn` が利用者のローカル日付より前のときだけであることが必須である。当日は超過にしてはならない。期限が無いタスクと、完了済みのタスクは超過にしてはならない。

#### Scenario: 空のタスク一覧
- **とき** タスクがまだ無い状態で `/` を開く
- **ならば** タスクが無いことが分かる
- **かつ** タスク登録への導線がある
- **かつ** 削除操作は無い
- **かつ** select があり、選択は「全員」である

#### Scenario: 一覧は新しいタスクが上である
- **とき** 作成日時が異なるタスクが 2 件以上ある状態で `/` を開く
- **ならば** `createdAt` が新しいタスクが上に出る
- **かつ** 各項目に担当者名、完了、作成日時が出る
- **かつ** カードからそのタスクの詳細へ遷移できる
- **かつ** 一覧に削除は無い

#### Scenario: 完了済みも一覧に残る
- **とき** `done` が true のタスクと false のタスクがある状態で `/` を開く
- **ならば** 両方とも一覧に出る
- **かつ** 一覧に完了の切り替えは無い
- **かつ** 一覧に担当者の変更は無い

#### Scenario: 初期は全員である
- **とき** 担当者が異なるタスクがある状態で `/` を開く
- **ならば** select の選択は「全員」である
- **かつ** 「全員」の値は、どのメンバーの `id` でもない
- **かつ** 全件が出る
- **かつ** URL に絞り込みは無い

#### Scenario: 選択肢はメンバーの id である
- **とき** メンバーが 2 人以上いる状態で `/` の select を見る
- **ならば** 「全員」の次に、GET `/api/members` のメンバーが API の順で並ぶ
- **かつ** 各メンバーの表示は `name` である
- **かつ** 各メンバーの値は `id` である

#### Scenario: 同名でも id で区別する
- **とき** 同じ `name` で `id` が異なるメンバーが 2 人いる状態で `/` の select を見る
- **ならば** 選択肢は 2 つある
- **かつ** 値は互いに異なる `id` である

#### Scenario: 1 人を選ぶとその担当だけが残る
- **とき** 担当者が異なるタスクがあり、その中に完了済みがある状態で、1 人の `id` を選ぶ
- **ならば** 出るタスクは、その `id` と `assigneeId` が一致するものだけである
- **かつ** その人の完了済みも残る
- **かつ** 並びは `createdAt` の降順のままである
- **かつ** 他の担当のタスクは出ない
- **かつ** URL に絞り込みは無い

#### Scenario: 全員に戻すと全件に戻る
- **とき** 1 人を選んだあと、「全員」に戻す
- **ならば** 全件が出る
- **かつ** 完了済みも出る

#### Scenario: 詳細から戻ると全員である
- **とき** 1 人を選んだ一覧から詳細を開き、一覧へ戻る
- **ならば** 選択は「全員」である
- **かつ** 全件が出る
- **かつ** URL に絞り込みは無い

#### Scenario: 選んだメンバーが無いと全員に戻る
- **とき** 選んでいる `id` のメンバーが GET `/api/members` に無い
- **ならば** 選択は「全員」に戻る
- **かつ** 全件が出る

#### Scenario: 0 件でも select は残る
- **とき** 担当タスクが無いメンバーを選ぶ
- **ならば** タスクが無いことが分かる
- **かつ** select は残る
- **かつ** その選択は、選んだメンバーのままである

#### Scenario: 期限は一覧に出る
- **とき** `dueOn` があるタスクを `/` で見る
- **ならば** その `YYYY-MM-DD` がカードの中に出る
- **かつ** `body` の全文は一覧に出ない

#### Scenario: 完了日は一覧に出る
- **とき** `completedAt` があるタスクを `/` で見る
- **ならば** 「完了日」と、その UTC ISO8601 の文字が出る

#### Scenario: 完了日が無いタスクは完了日を出さない
- **とき** `completedAt` が null のタスクを `/` で見る
- **ならば** 「完了日」は出ない

#### Scenario: タスクを登録はナビゲーションにある
- **とき** `/` を開く
- **ならば** 「タスクを登録」はナビゲーションの中にある
- **かつ** そのリンク先は `/new` である
- **かつ** 「メンバー」も同じナビゲーションにあり、「タスクを登録」より前である
- **かつ** 画面右下には固定されていない
### Requirement: タスク登録は /new である
システムは画面 `/new` でタスク登録を必須で提供する。タイトルは必須である。内容 `body` と期限 `dueOn` を入力できることが必須である。どちらも空のまま登録できることが必須である。担当者を選ばせてはならない。登録に成功したならば一覧 `/` へ必須で戻る。完了の入力を出してはならない。タイトルを登録後に変える入力を出してはならない。

#### Scenario: タイトルは必須である
- **とき** 利用者がタイトル空のまま `/new` で登録しようとする
- **ならば** タスクは追加されない
- **かつ** タイトルが必須であることが分かる

#### Scenario: 担当者は選ばせない
- **とき** 利用者が `/new` を開く
- **ならば** 担当者を選ぶ入力は無い
- **かつ** タイトルを入れて登録に成功すると `/` へ戻る

#### Scenario: 内容と期限を入れて登録する
- **とき** 利用者が `/new` でタイトル、内容、期限を入れて登録する
- **ならば** 登録に成功すると `/` へ戻る
- **かつ** そのタスクの詳細に、入れた内容が出る
- **かつ** 一覧に、入れた期限の `YYYY-MM-DD` が出る
### Requirement: タスク詳細は /tasks/:id である
システムは画面 `/tasks/:id` で、そのタスクのタイトル、担当者名、完了、作成日時、内容 `body` を必須で出す。`dueOn` があるときは、その `YYYY-MM-DD` を出すことが必須である。`completedAt` があるときは、「完了日」と、その UTC ISO8601 の文字を出すことが必須である。`completedAt` が null のときは「完了日」を出してはならない。内容は平文であることが必須である。Markdown として描画してはならない。内容と期限を編集できることが必須である。タイトルを編集する入力を出してはならない。削除は confirm のあとだけ実行することが必須である。削除に成功したならば `/` へ必須で戻る。存在しない id は、見つからないことが分かる表示で必須である。担当者を、存在するメンバーの中から選んで変えられることが必須である。完了を切り替えられることが必須である。候補に、存在しないメンバーを出してはならない。一覧に担当者の変更と完了の切り替えを置いてはならない。

#### Scenario: 詳細を見て confirm 後に削除する
- **とき** 利用者が存在するタスクの詳細を開き、削除を confirm する
- **ならば** そのタスクはハード削除される
- **かつ** `/` へ戻る
- **かつ** 一覧にそのタスクは無い

#### Scenario: confirm を拒否すると削除されない
- **とき** 利用者が詳細で削除を始め、confirm を拒否する
- **ならば** タスクは残る
- **かつ** 画面は詳細のままである

#### Scenario: 存在しないタスクは見つからない
- **とき** 利用者が存在しない id の `/tasks/:id` を開く
- **ならば** 見つからないことが分かる

#### Scenario: 詳細に担当者変更と完了切替は無い
- **とき** 利用者がタスク詳細を見る
- **ならば** 担当者を変える操作がある
- **かつ** 完了を切り替える操作がある
- **かつ** その候補は存在するメンバーだけである

#### Scenario: 詳細で担当者を変える
- **とき** 利用者が詳細で、別の存在するメンバーを担当者に選ぶ
- **ならば** そのタスクの担当者名は選んだメンバーになる
- **かつ** 他のタスクの担当者は変わらない

#### Scenario: 詳細で完了を切り替える
- **とき** 利用者が詳細で完了を切り替える
- **ならば** そのタスクの完了の文言が切り替わる
- **かつ** 一覧に戻ってもそのタスクは残る
- **かつ** 一覧に完了の切り替えは無い

#### Scenario: 内容は詳細に出る
- **とき** 内容があるタスクの詳細を開く
- **ならば** その内容が平文で出る
- **かつ** Markdown としては描画されない

#### Scenario: 完了にすると完了日が出る
- **とき** 利用者が未完了のタスクを詳細で完了にする
- **ならば** 「完了日」と、UTC ISO8601 の文字が出る

#### Scenario: 未完了に戻すと完了日が消える
- **とき** 利用者が完了済みのタスクを詳細で未完了に戻す
- **ならば** 「完了日」は出ない
### Requirement: メンバー画面は /members だけである
システムは画面 `/members` で、メンバーの登録と一覧と削除を必須で提供する。一覧は `createdAt` の降順で必須である。削除は confirm のあとだけ実行することが必須である。メンバーの詳細画面を提供してはならない。メンバーが無いときは、メンバーが無いことが分かる表示で必須である。

#### Scenario: メンバーを登録して一覧に出る
- **とき** 利用者が `/members` で名前を登録する
- **ならば** そのメンバーが一覧に出る
- **かつ** 新しいメンバーが上に出る
- **かつ** 詳細画面へは遷移しない

#### Scenario: メンバー削除は confirm 後である
- **とき** 利用者が `/members` で、担当タスクの無いメンバーの削除を confirm する
- **ならば** そのメンバーはハード削除される
- **かつ** 一覧から消える

#### Scenario: confirm を拒否するとメンバーは残る
- **とき** 利用者が `/members` で削除を始め、confirm を拒否する
- **ならば** メンバーは残る
### Requirement: API は一段目のパスだけである
システムが提供する API は、GET と POST の `/api/members`、DELETE の `/api/members/{id}`、GET と POST の `/api/tasks`、GET と DELETE と PATCH の `/api/tasks/{id}` だけであることが必須である。絞り込み用の API を提供してはならない。これ以外のパスを作ってはならない。

#### Scenario: 一覧と作成と詳細と削除だけがある
- **とき** クライアントが上記のパスを所定のメソッドで呼ぶ
- **ならば** その操作は契約どおりの結果を返す
- **かつ** PATCH は `/api/tasks/{id}` だけである
- **かつ** 絞り込み用の API は無い
### Requirement: 作成は 201、削除は 204、不在は 404、検証失敗は 422 である
メンバー作成とタスク作成の成功は 201 で必須である。メンバー削除とタスク削除の成功は 204 で必須である。存在しないタスクの GET と、存在しないメンバーまたはタスクの DELETE は 404 で必須である。検証失敗は 422 で必須である。検証失敗のときストアを変えてはならない。空の一覧 GET は 200 と空配列で必須である。

#### Scenario: 作成と削除の成功
- **とき** クライアントが妥当なメンバーまたはタスクを作成し、そのあと存在する対象を削除する
- **ならば** 作成の応答は 201 である
- **かつ** 削除の応答は 204 である

#### Scenario: 対象が無い
- **とき** クライアントが存在しない id でタスクを GET する、または存在しない id でメンバーかタスクを DELETE する
- **ならば** 応答は 404 である
- **かつ** ストアは変わらない

#### Scenario: 検証失敗はストアを変えない
- **とき** クライアントが検証に失敗する作成または削除を送る
- **ならば** 応答は 422 である
- **かつ** ストアの件数と中身は変わらない
### Requirement: メンバー項目は id、name、createdAt である
システムは各メンバーを JSON の camelCase で表し、項目は `id`（UUID）、`name`、`createdAt` だけであることが必須である。`id` と `createdAt` はサーバが付与することが必須である。`createdAt` は UTC の ISO8601 で必須である。クライアントが送った `id` と `createdAt` を採用してはならない。保存する `name` は strip 後の値で必須である。

#### Scenario: 作成したメンバーは所定の項目を返す
- **とき** クライアントが名前でメンバーを作成する
- **ならば** 応答は `id`、`name`、`createdAt` を含む
- **かつ** `createdAt` は UTC の ISO8601 である
- **かつ** クライアントが `id` を送っても、保存される `id` はサーバの UUID である
### Requirement: タスク項目は id、title、assigneeId、done、createdAt である
システムは各タスクを JSON の camelCase で表し、項目は `id`（UUID）、`title`、`assigneeId`、`done`、`createdAt`、`body`、`dueOn`、`completedAt` であることが必須である。タスク JSON に `name` を持ってはならない。`id` と `createdAt` はサーバが付与することが必須である。`createdAt` は UTC の ISO8601 で必須である。保存する `title` は strip 後の値で必須である。`body` は平文の文字列であることが必須である。省略と、strip 後の空文字は許すことが必須である。文字列でない `body` は 422 で必須である。`dueOn` は、実在する暦日の `YYYY-MM-DD`、空文字、null、または省略であることが必須である。空文字と null は期限なしであることが必須である。それ以外の形は 422 で必須である。`completedAt` は、UTC の ISO8601 または null であることが必須である。クライアントが `completedAt` を決めてはならない。保存済みで `body`、`dueOn`、`completedAt` が無いタスクは、読むときに `body` を空文字、`dueOn` と `completedAt` を null として返すことが必須である。GET（一覧・詳細）はこれら 8 キーを返すことが必須である。

#### Scenario: 作成したタスクは所定の項目を返す
- **とき** クライアントがタイトルでタスクを作成する
- **ならば** 応答は `id`、`title`、`assigneeId`、`done`、`createdAt`、`body`、`dueOn`、`completedAt` を含む
- **かつ** `name` という項目は存在しない
- **かつ** `createdAt` は UTC の ISO8601 である
- **かつ** `body` は空文字である
- **かつ** `dueOn` は null である
- **かつ** `completedAt` は null である

#### Scenario: 古いタスクは欠けた項目を補って返す
- **とき** クライアントが、`body`、`dueOn`、`completedAt` を保存していないタスクを GET する
- **ならば** 応答の `body` は空文字である
- **かつ** `dueOn` は null である
- **かつ** `completedAt` は null である

#### Scenario: 文字列でない内容は拒否する
- **とき** クライアントが文字列でない `body` でタスクを作成する、または PATCH する
- **ならば** 応答は 422 である
- **かつ** ストアは変わらない

#### Scenario: 期限の形が違うと拒否する
- **とき** クライアントが、`YYYY-MM-DD` の実在する暦日でも、空文字でも、null でもない `dueOn` を送る
- **ならば** 応答は 422 である
- **かつ** ストアは変わらない
### Requirement: name と title は strip 後に空なら 422 である
`name` は strip 後に空なら 422 で必須である。`title` は strip 後に空なら 422 で必須である。省略も 422 で必須である。同名のメンバーは許すことが必須である。

#### Scenario: 空の名前は拒否する
- **とき** クライアントが空、または空白だけの `name` でメンバーを作成する
- **ならば** 応答は 422 である
- **かつ** メンバーは増えない

#### Scenario: 空のタイトルは拒否する
- **とき** クライアントが空、または空白だけの `title` でタスクを作成する
- **ならば** 応答は 422 である
- **かつ** タスクは増えない

#### Scenario: 同名メンバーは許す
- **とき** クライアントが同じ `name` のメンバーを 2 人作成する
- **ならば** 両方とも 201 である
- **かつ** `id` は互いに異なる
### Requirement: タスク POST の assigneeId と done は採用しない

`PATCH /api/tasks/{id}` は、送った `assigneeId`、`done`、`body`、`dueOn` だけを、そのタスクについて変えることが必須である。そのうちの一部だけでも更新できることが必須である。4 つとも省略は 422 で必須である。空、または空白だけの `assigneeId` は 422 で必須である。存在しないメンバーへの `assigneeId` は 422 で必須である。boolean でない `done` は 422 で必須である。文字列でない `body` は 422 で必須である。`YYYY-MM-DD` の実在する暦日でも、空文字でも、null でもない `dueOn` は 422 で必須である。これらのどれかが検証失敗のとき、他が妥当でも 422 で必須である。422 のときストアを変えてはならない。存在しないタスクは、本文の検証より先に 404 で必須である。`id`、`createdAt`、`title`、`completedAt` は不変で必須である。PATCH にこれらが付いていても捨て、422 にはしないことが必須である。`title` の保存値は変えてはならない。`dueOn` を省略したときは、保存済みの `dueOn` を変えてはならない。空文字か null の `dueOn` は、期限なしとして null にすることが必須である。`body` を省略したときは、保存済みの `body` を変えてはならない。`done` が false から true になったとき、`completedAt` に今の UTC ISO8601 を付けることが必須である。すでに `done` が true のタスクへ、もう一度 true を送ったときは、元の `completedAt` を残すことが必須である。`done` が true から false になったとき、`completedAt` を null にすることが必須である。`done` を省略したときは、`completedAt` を変えてはならない。他のタスクを再割り当てしてはならない。存在しないタスクの PATCH は 404 で必須である。404 のときストアを変えてはならない。成功は 200 で必須である。応答は `id`、`title`、`assigneeId`、`done`、`createdAt`、`body`、`dueOn`、`completedAt` の 8 キーであることが必須である。タスク JSON に `name` を足してはならない。タスク POST の `assigneeId` と `done` は採用してはならない。新規の `done` は false のままであることが必須である。新規の `completedAt` は null のままであることが必須である。
